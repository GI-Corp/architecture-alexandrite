# Архитектурное решение по кешированию

## 1. Мотивация

В текущей системе MES (Manufacturing Execution System) наблюдаются значительные задержки при загрузке дашбордов заказов. Операторы жалуются на низкую скорость, из-за чего теряется производительность и, как следствие, — доход компании. Новые клиенты также отмечают медленную обработку заказов.

Эти проблемы вызваны высокой нагрузкой на базу данных и отсутствием быстрой повторной выборки часто используемых данных. Кеширование — эффективное решение, позволяющее снизить время отклика, уменьшить нагрузку на БД и повысить пользовательский опыт.

Кешировать стоит:

- Списки заказов, отображаемые в дашбордах MES
- Страницы с часто повторяющимися фильтрами (например, `userId + статус заказа`)
- Отдельные справочные данные и рекомендации в модуле eShop
- Неперсонализированные CRM-данные (требуется уточнение)

Не подлежит кешированию:

- Просчёт стоимости заказов — индивидуальные данные и параметры, высокий риск устаревания, критична точность.

## 2. Предлагаемое решение

### Тип кеширования

**Серверное кеширование** — основной выбор, поскольку:

- Данные чувствительны, особенно в MES
- Обеспечивает контроль и централизованное обновление
- Лучше управляется в масштабах системы

Клиентское кеширование может быть уместно в eShop (например, для рекомендаций), но это второстепенный случай и не решает корневую проблему MES.

### Паттерн кеширования

Выбран паттерн **Cache-Aside**, по причине:

- Прост в реализации и внедрении
- Позволяет избежать избыточной зависимости от кеша
- Позволяет контролировать, когда и какие данные кешируются

#### Альтернативные паттерны и почему они не подходят:

| Паттерн            | Причина отказа                                  |
|--------------------|--------------------------------------------------|
| Read-Through       | Сильно связывает бизнес-логику с кешем          |
| Refresh-Ahead      | Создает ненужную фоновую нагрузку на БД         |
| Write-Through      | Основной фокус — запись, а не чтение            |
| Write-Behind       | Потенциальная потеря данных при сбоях кеша      |

### Инвалидация кеша

#### Предлагаемые стратегии:

1. **Инвалидация по ключу** — удобна при использовании уникальных шаблонов ключей (например, `{userId}_orders_status`).
2. **Инвалидация при изменении** — при обновлении данных (например, смене статуса заказа) кеш обновляется вручную.
3. **Программная инвалидация** — применяется в сложных случаях (например, при каскадных изменениях данных).

#### Причины выбора:

| Стратегия                  | Преимущества                         | Недостатки                          |
|----------------------------|--------------------------------------|-------------------------------------|
| По времени (TTL)           | Простота                             | Возможность устаревших данных       |
| По ключу                   | Контроль, гибкость                   | Зависимость от структуры ключей     |
| При изменении              | Гарантия актуальности                | Требует внедрения хуков или событий |
| Программная                | Максимальный контроль                | Усложнение кода и поддержки         |

**Выбранные стратегии:**

- **При изменении** — для заказов и дашбордов
- **По ключу** — для eShop, CRM и других менее чувствительных данных
- **TTL (опционально)** — как механизм последнего рубежа

### Сравнение альтернативных решений

#### Выбранные стратегии:

| Стратегия                           | Плюсы                                                           | Минусы                                                    | Применимость |
| ----------------------------------- | --------------------------------------------------------------- | --------------------------------------------------------- | ------------ |
| **Инвалидация на основе изменений** | - Обеспечивает актуальные данные<br>- Хороший контроль          | - Требует подписки на изменения<br>- Сложнее в реализации |  Да         |
| **Программная инвалидация**         | - Гибкость<br>- Возможность управления логикой удаления         | - Добавляет сложность в коде<br>- Требует дисциплины      |  Да         |
| **Инвалидация по ключу**            | - Простая реализация<br>- Можно настроить на конкретные события | - Высокая зависимость от ключей<br>- Возможны коллизии    |  Да         |
| Временная (TTL) инвалидация         | - Легко реализуется<br>- Подходит для редко обновляемых данных  | - Возможна устаревшая информация<br>- Не подходит для MES |  Нет        |
| Инвалидация на основе запросов      | - Автоматически управляет ключами                               | - Многообразие ключей, сложная трассировка                |  Нет        |

#### Вывод

Для проекта MES наиболее оправданы:

* **Инвалидация на основе изменений** — позволяет сохранять данные в актуальном состоянии после обновлений в БД.
* **Программная инвалидация** — обеспечит гибкость и контроль, особенно в частных кейсах.
* **Инвалидация по ключу** — будет полезной в простых сценариях и поможет контролировать данные по заказам.
