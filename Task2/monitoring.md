# Внедрение мониторинга: стратегический подход к стабильности и росту системы

## 1. Зачем это нужно

На текущем этапе система работает как "black box (черный ящик)" — о проблемах мы узнаём постфактум, чаще всего от пользователей. Это снижает скорость реакции, влияет на доверие и может приводить к финансовым потерям.

Наша цель — обеспечить наблюдаемость системы, при которой сбои выявляются до того, как повлияют на клиентский опыт. Мониторинг позволяет:

- оперативно реагировать на инциденты;
- выявлять и устранять узкие места;
- понимать поведение пользователей и нагрузку на систему;
- принимать обоснованные решения о масштабировании и развитии продукта.

В результате улучшается стабильность, растёт удовлетворённость клиентов и повышается конкурентоспособность решения.

---

## 2. Методология мониторинга

Для охвата разных типов компонентов мы используем несколько проверенных подходов:

- **USE (Utilization, Saturation, Errors)** — подходит для анализа инфраструктурных сервисов, в частности **MES**, где важно понимать нагрузку и пики потребления ресурсов.
- **RED (Rate, Errors, Duration)** — используется для HTTP-сервисов: `eshop`, `CRM`, `MES API`, позволяя отслеживать ошибки, задержки и интенсивность.
- **Четыре золотых сигнала** (latency, traffic, errors, saturation) — применимы системно: от мониторинга очередей и баз данных до оценки бизнес-критичных процессов.

## 3. Основные метрики

### API и нагрузка:

| Метрика | Назначение | Labels |
|--------|-------------|--------|
| RPS (eshop API) | Понимание нагрузки | `service`, `endpoint`, `method` |
| RPS (CRM API) | Понимание нагрузки | `service`, `endpoint`, `method` |
| RPS (MES API) | Понимание нагрузки | `service`, `endpoint`, `method` |
| Latency (eshop API) | Выявление медленных запросов | `service`, `endpoint`, `status_code` |
| Latency (MES API) | Влияние на производственную цепочку | `service`, `endpoint`, `status_code` |

| HTTP 500 (MES API) | Детектирование сбоев | `service`, `endpoint`, `status_code` |

### Ресурсы и инфраструктура:

| Метрика | Назначение | Labels |
|--------|-------------|--------|

## 4. План внедрения

- Развернуть **Prometheus** для сбора метрик
- Интегрировать экспортеры в каждый ключевой сервис
- Настроить **Grafana** с дешбордами:
  - RED (для каждого API-сервиса)
  - USE (для MES)
  - Golden signals (системный уровень)
- Настроить **alerting** в Prometheus
- Развернуть **ELK-стек**
- Настроить **ILM (Index Lifecycle Management)** для Elasticsearch
- Подключить логирование через **Filebeat** или **Logstash**
- Создать дешборды в **Kibana**:
  - по HTTP-ошибкам (500, 400)
  - по бизнес-событиям (расчёт стоимости, создание заказов)

## 5. Критические алерты и действия

| Показатель | Порог | Действие |
|------------|--------|----------|
| CPU (MES API) | > 90% | Алерт DevOps, автоскейлинг при необходимости |
| HTTP 500 (любой сервис) | > 50 в сек | Алерт команде, уведомление тимлиду |
| Очередь (price_calc_queue) | > 1000 сообщений | Алерт DevOps, анализ блокировок |
| Dead-letter queue | > 100 за 10 минут | Алерт DevOps и backend, ручной разбор |
| RPS (eshop API) | > 10 000 в сек | Алерт, возможный DDoS |
| RPS (MES API) | > 10 000 в сек | Алерт, возможная самонагрузка |
| Hot index в Elasticsearch | > 50GB или > 7 дней | Проверка работы ILM, возможный перенос вручную |
