# Архитектурное решение по трейсингу

## 1. Анализ системы и определение зон покрытия

### Узкие места, где заказ может "зависнуть" или потеряться:

* `eshop` → RabbitMQ (отправка заказа на расчёт)
* `MES` → RabbitMQ (ответ с расчётом стоимости)
* `MES` → `CRM` (обновление статуса после расчёта)
* `CRM` → `MES` (подтверждение начала производства)
* `MES` → `CRM` (завершение производства и упаковки)
* Партнёры → `MES API` (запросы от B2B через публичный API)
* Все HTTP-запросы между сервисами
* Все сообщения в RabbitMQ (как отправка, так и получение)
* `MES` → S3 (получение 3D-модели)
* `eshop` → S3 (загрузка 3D-модели)

### Список данных для включения в трейсинг:

* `trace_id`
* `span_id`
* `order_id`
* `user_id`
* `source_service` — инициатор
* `target_service` — получатель
* `operation_name` — название операции
* `status` — HTTP-код
* `error_message` — описание ошибки, если она была
* `message_id` — идентификатор сообщения (для RabbitMQ)
* `s3_object_key` — идентификатор объекта в S3

## 2. Мотивация

Сейчас команда узнаёт о проблемах только после жалоб клиентов. При этом отладка сложна: непонятно, где именно заказ "застрял" или потерялся. Это приводит к:

* недовольству клиентов и партнёров,
* значительным затратам времени на ручную диагностику,
* потерям в бизнесе.

Внедрение трейсинга обеспечит:

* прозрачную трассировку жизненного цикла заказа,
* сокращение времени поиска и устранения сбоев,
* повышение надёжности и доверия клиентов.

### Влияние на метрики:

**Технические:**

* MTTR (Mean Time to Recovery) — сократится
* Процент "зависших" заказов — снизится
* Количество ручных расследований инцидентов — снизится

**Бизнесовые:**

* Уровень удовлетворённости клиентов — повысится
* Потери заказов и доходов — сократятся

## 3. Предлагаемое решение

### Стек:

* **OpenTelemetry SDK** — внедряется во все сервисы (`eshop`, `MES`, `CRM`)
* **Jaeger** — централизованная система визуализации трейсинга

### Поддерживаемые источники:

* HTTP-запросы
* RabbitMQ (producer + consumer)
* Взаимодействие с S3
* Внутренние операции в сервисах

### Реализация:

* В каждый микросервис встраивается OpenTelemetry SDK.
* SDK автоматически собирает спаны по всем входящим/исходящим HTTP-запросам, сообщениям в очередь и обращениям к S3.
* Все трейсинг-данные отправляются в Jaeger, установленный в пределах инфраструктуры.
* Настраиваются уникальные `trace_id` и `span_id` для каждой операции с заказом, чтобы видеть всю цепочку.

## 4. Компромиссы

* Не все проприетарные/внешние компоненты можно заставить логировать трейсинг (например, некоторые партнёрские API).
* Сложность внедрения в старые или монолитные компоненты без REST/AMQP-интерфейсов.
* Возможны накладные расходы на производительность (небольшие) при массовой генерации спанов.
* Требуется доработка CI/CD пайплайнов, чтобы поддерживать единую конфигурацию SDK.

## 5. Безопасность

* Доступ к Jaeger будет защищён корпоративной аутентификацией (SAML/OIDC).
* Разграничение прав: только пользователи с ролью `Поддержка` или `DevOps` смогут просматривать трейсинг.
* Доступ снаружи запрещён фаерволами и внутренними политиками безопасности.
* Все trace-данные передаются по TLS внутри сети.
* Логи, содержащие персональные данные, маскируются или исключаются из трейсинга.

## 6. Автоматический мониторинг и алертинг (доп. задание)

* Поверх собранных трейсинг-данных настраивается **Grafana** + **Tempo (или Jaeger plugin)**.
* Метрики по длительности и статусам операций (например, долгий расчёт стоимости, неудачный вызов S3) передаются в **Prometheus**.
* Настраиваются алерты на:

  * Длительное ожидание ответа на ключевых участках (e.g. MES → CRM)
  * Частые ошибки по определённому `operation_name`
  * Отсутствие trace по заказу дольше заданного SLA
