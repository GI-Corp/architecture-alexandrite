# Архитектурное решение по логированию

## 1. Анализ системы и планирование логирования

Для повышения прозрачности работы сервисов и упрощения диагностики проблем, планируется систематический сбор логов из ключевых компонентов системы.

### Сбор логов (уровень INFO):

| Событие                              | Данные для логирования                                       |
|--------------------------------------|---------------------------------------------------------------|
| Изменение статуса заказа             | Время, идентификатор покупателя, номер заказа                |
| Создание нового заказа               | Время, идентификатор покупателя, номер заказа                |
| Загрузка 3D-модели                   | Время, ID пользователя, номер заказа, имя и размер файла     |
| Скачивание 3D-модели MES-сервисом   | Время, номер заказа, имя файла, результат                    |
| Обновление данных из CRM             | Время, номер заказа, инициатор, изменённые поля              |
| Начало расчёта стоимости             | Время, номер заказа, название сервиса                        |
| Завершение расчёта стоимости         | Время, номер заказа, итоговая стоимость, длительность        |
| Отправка сообщения в очередь         | Время, название очереди, номер заказа, ID сообщения          |
| Получение сообщения из очереди      | Время, название очереди, номер заказа, ID сообщения, результат обработки |

### Дополнительные уровни логирования:

- `DEBUG` — используется в тестовых/стейджинг-окружениях для отладки
- `WARN` — логируются нестандартные, потенциально опасные ситуации (таймауты, повторные попытки)
- `ERROR` — ошибки, влияющие на бизнес-процессы (например, невозможность рассчитать стоимость)

### Источники логов на C4-диаграмме:

Необходимо собирать логи из следующих компонентов:
- Eshop
- CRM
- MES
- Очереди сообщений (RabbitMQ или Kafka)

> Все источники логов помечены на C4-схеме стрелками к центральному логгеру (Logstash).

## 2. Мотивация

В текущей ситуации разработчики и поддержка узнают о проблемах от пользователей, а не от системы. Это ведёт к задержкам в реагировании, сложностям в воспроизведении инцидентов и увеличению нагрузки на команду.

### Метрики, на которые влияет логирование:

- Снижение времени анализа инцидентов
- Повышение скорости реакции на ошибки
- Сокращение количества обращений в поддержку
- Снижение времени обработки заказов
- Снижение числа «зависших» заказов

### Приоритетные компоненты для внедрения логирования:

1. **MES** — ключевой производственный сервис, критичен для бизнеса
2. **CRM** — управляет коммуникациями, финансами, уведомлениями
3. **Eshop** — фронтовой сервис, где начинается бизнес-процесс

## 3. Предлагаемое решение

### Технологический стек:

- **Elasticsearch** — хранилище логов и аналитика
- **Logstash** — сбор, фильтрация и отправка логов
- **Kibana** — визуализация, поиск и анализ логов

Все сервисы будут логировать события в stdout или файл, далее логи собираются Filebeat/Logstash-агентами и отправляются в Elasticsearch.

### Обновления в C4-схеме:

- Добавлен компонент `ELK-стек`
- Все сервисы подключены к Logstash
- Kibana доступна DevOps и разработке

### Политика безопасности:

- Чувствительные данные (персональные, финансовые) будут маскированы (например, email → `***@domain.com`)
- Доступ к Kibana ограничен через RBAC (DevOps, поддержка, ответственные разработчики)
- Все соединения между компонентами ELK-стека — через TLS

### Политика хранения:

- Хранение логов — 30 дней по умолчанию
- Логи разбиваются по индексам (например, по названию сервиса)
- Сжатие и ротация на уровне Elasticsearch

## 4. Превращение в систему анализа логов

### Алерты:

- Увеличение количества 5xx ответов
- Просчёт стоимости дольше заданного порога (например: > 10 минут)
- Ошибки подключения к внешним системам

### Аномалии:

- Всплеск заказов за секунду — возможный DDoS
- Резкий рост времени расчёта стоимости — перегрузка MES
- Много заказов — но RabbitMQ пуста — сбой в очереди
- Заказ многократно переходит в один и тот же статус — ошибка в логике

## 5. Критерии выбора технологии логирования

| Критерий                    | ELK                          | OpenSearch                  | Splunk                   | Graylog                  |
|-----------------------------|-------------------------------|-----------------------------|--------------------------|--------------------------|
| Лицензия                    | Elastic License               | Apache 2.0                  | Проприетарная            | GPLv3                    |
| Масштабируемость            | Хорошая                       | Отличная                    | Отличная                 | Средняя                  |
| Установка/поддержка         | Требует усилий                | Относительно проще          | Лёгкая (в облаке)         | Простая                  |
| Стоимость владения          | Средняя (Self-hosted)         | Низкая                      | Высокая                  | Низкая                   |
| Комьюнити и документация    | Широкое сообщество            | Молодое, но активно растёт  | Профессиональное сообщество | Хорошее                  |
| Поддержка RBAC и маскировки | Частично (в платной версии)   | Да                          | Да                       | Да                       |

### Выбор:

**OpenSearch** — как альтернатива ELK, приоритетен для open-source и легальной совместимости.  
**ELK** — подходит, если уже используется и есть опыт в команде.  
**Splunk** — мощный, но дорогой. Использовать только при больших бюджетах.  
**Graylog** — подходит для простых систем, но имеет ограничения в масштабируемости.
