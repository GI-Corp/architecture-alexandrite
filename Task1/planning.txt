# Проектная работа. Спринт 4 — Задание 1  
## Анализ текущей архитектуры и план по устранению проблем

### I. Анализ архитектуры и идентификация проблемных узлов

В результате анализа архитектуры системы компании «Александрит», а также на основе диаграммы C4 и описания бизнес-процессов, были выявлены ключевые уязвимости, ограничивающие масштабируемость, отказоустойчивость и техническую гибкость системы. Проблемы касаются как технологического стека, так и архитектурных решений, принятых на раннем этапе развития продукта.

#### Ключевые проблемные зоны:

1. **Отсутствие централизованного управления доступом (Identity Management)**  
   На диаграмме отсутствует отдельный компонент, отвечающий за аутентификацию и авторизацию пользователей (включая пользователей API и операторов). Это создаёт потенциальные риски безопасности и затрудняет унификацию политики доступа.

2. **Слишком монолитная структура Web-приложения**  
   Web-приложение объединяет несколько крупных бизнес-доменов, что затрудняет масштабирование, сопровождение и развитие. Это также повышает риски каскадных сбоев при изменениях.

3. **Отсутствие горизонтального масштабирования компонентов**  
   Приложения развёрнуты по одному инстансу. При росте нагрузки масштабирование требует дублирования всего приложения, даже если перегружен лишь один модуль (например, расчёт стоимости).

4. **Единая точка отказа — база данных**  
   Все модули системы завязаны на один инстанс PostgreSQL без репликации. Любая проблема с базой данных ведёт к полной недоступности сервисов.

5. **Невысокая устойчивость к сбоям сторонних API**  
   Отсутствует явная реализация отказоустойчивости при взаимодействии с внешними API. Не описаны fallback-механизмы, повторные попытки или альтернативные сценарии обработки ошибок.

6. **Слабая изоляция бизнес-доменов в сервисном слое**  
   Бизнес-логика централизована в одном слое без выделения по доменам. Это снижает гибкость и приводит к высокой связанности между модулями.

7. **Отсутствие слоёв кэширования**  
   Не реализовано кэширование на уровне данных и представления. Это создаёт лишнюю нагрузку на базу данных и увеличивает время отклика, особенно в высоконагруженных сценариях (например, загрузка дашборда операторов MES).

8. **Отсутствие централизованного мониторинга, логирования и трассировки**  
   На текущий момент отсутствуют решения для сбора метрик, логов и трассировки запросов. Это затрудняет обнаружение проблем в продакшене и затягивает реакцию на инциденты.

### II. Предложенные инициативы для устранения проблем

Для устранения текущих и потенциальных проблем предлагаются следующие инициативы — как архитектурные, так и организационные:

#### 1. Внедрение системы централизованной аутентификации и авторизации  
Реализовать **SSO** на базе решений вроде Keycloak, Auth0 или IdentityServer. Обеспечить поддержку OAuth 2.0 и OpenID Connect. Это позволит унифицировать доступ во всех системах и упростит масштабирование безопасности.

#### 2. Внедрение API Gateway  
Добавить API-шлюз (например, Kong, NGINX или Spring Cloud Gateway) для маршрутизации, валидации, защиты от DDoS, и аудита. Все внешние и внутренние вызовы должны проходить через шлюз.

#### 3. Рефакторинг и выделение микросервисов по бизнес-доменам  
Рекомендуется выделить ключевые домены в отдельные сервисы:
- `Auth Service`
- `User Management`
- `Order Management`
- `Pricing/Cost Calculation`
- `Payment Service`

Это упростит масштабирование и изоляцию изменений.

#### 4. Повышение отказоустойчивости базы данных  
Настроить репликацию PostgreSQL (primary-replica), резервное копирование и автоматическое восстановление. Рассмотреть возможность масштабирования чтения через реплики и/или внедрение read/write separation.

#### 5. Устойчивость внешних API через Circuit Breaker & Retry  
Реализовать шаблоны отказоустойчивости (например, через Polly, Resilience4J). Хранить последний успешный ответ в Redis для критичных операций.

#### 6. Внедрение системы кэширования  
Использовать Redis для кэширования частых данных: статусы заказов, 3D-модели, отображение на дашборде. Использовать подходы с TTL и обновлением по событиям.

#### 7. Переход к событийной архитектуре  
Внедрить **Event Bus** (RabbitMQ или Kafka). Использовать событийный подход (Event-Driven Design) и, при необходимости, SAGA-паттерн для распределённых транзакций.  
Ключевые события: `OrderInitiated`, `PriceCalculated`, `ManufacturingStarted`, `Shipped`, и др.

#### 8. Набор инструментов для наблюдаемости (Observability Stack)  
- **Логирование**: ELK Stack (Elasticsearch + Logstash + Kibana)  
- **Мониторинг**: Prometheus + Grafana, RED-метрики  
- **Трейсинг**: Jaeger для распределённой трассировки

#### 9. Создание адаптеров для внешних API  
Добавить слой абстракции (анти-коррупционный слой) для минимизации зависимости от сторонних API и поддержки обратной совместимости.

### IV. Целевая архитектура через полгода

Через полгода система должна перейти от монолитного решения к **сервисно-ориентированной архитектуре** (SOA) с частично микросервисным подходом, устойчивой инфраструктурой, централизованной безопасностью и высокой наблюдаемостью.

**Ключевые характеристики целевой архитектуры:**
- Централизованный доступ через SSO и API Gateway
- Выделенные микросервисы на ключевые бизнес-домены
- Реплицируемая база данных с бэкапами
- Кэш на Redis для ускорения частых операций
- Событийное взаимодействие между сервисами через RabbitMQ/Kafka
- Полная Observability Stack: логирование, мониторинг, трассировка

---

### V. Выбор трёх приоритетных инициатив

Если ограничиться только тремя инициативами в течение ближайших шести месяцев, следует выбрать:

1. **SSO + API Gateway**  
   Это основа безопасности, управления доступом и дальнейшего масштабирования.

2. **Мониторинг, логирование и трассировка**  
   Без инструментов наблюдаемости невозможно поддерживать SLA, определять узкие места и управлять инцидентами.

3. **Повышение отказоустойчивости базы данных + Кэширование**  
   Это критично для обеспечения стабильности и производительности при росте количества заказов и пользователей.
